# 当前连接器的加固评估

日期：2026-11-08。范围：当前工作区产品代码、现有测试、本机脱敏运行诊断和目录权限；未修改产品代码、权限、绑定或运行实例。未做渗透测试、断电故障注入、依赖漏洞扫描或持续压测。源码基线 HEAD 为 b365733；既有锁文件差异及其他未提交设计文件未改动。

## 判断

现有 Core / WeChat / Windows / 桌面装配的分层适合这个单用户本机连接器，应保留。加固优先级是目标与按键语义正确、单次执行可终止、状态可恢复、资源有上限。当前有保护基础，但不宜称为已证明可以长期无人值守运行。

推荐结构仍是一个桌面主进程、一个受控的按需输入 helper、现有本地加密文件。不要引入常驻系统服务、管理员权限、微服务、Redis、消息中间件或自研加密。任何可靠性承诺均受 Windows 焦点、目标应用行为和外部微信协议限制；不承诺跨应用输入恰好一次或保证写入成功。

## 已有基础，可继续使用

- MessageParser 检查 owner→bot、私聊、消息完成状态，忽略机器人回声；Coordinator 二次校验身份和消息关联。接口只接受 HTTPS 的微信域名，关闭自动重定向；单响应限制 1 MiB，网络请求有各自超时。
- 凭据及事件使用 DPAPI CurrentUser 保存，采用临时密文文件、Flush(true)、替换目标文件；序列化临时明文字节会清零。日志和诊断主要使用状态、计数和异常类型；当前 Git 索引未跟踪 .local、DPAPI 文件或 artifacts。
- 单实例互斥锁、输入串行锁、消息 ID 去重、输入前保存 Inserting、输入结果与回执同时保存；进程重启将未结束输入标为结果不明，不自动重发。
- 回执有稳定 client ID、99 普通＋1 查询容量、每秒请求限制、有效期和有限重试；回执失败不重新输入；helper 有 Job Object 和阶段记录基础。
- 当前自动输入策略已有密码、只读、选区、修饰键、输入法组合、交互桌面和完整性级别检查，但下述具体观察实现削弱了部分保护。

## 第一批：优先修复的实际边界

### 1. 真实焦点与输入目标判定

证据：[FocusedInputProbe.cs:264](D:/project/01-自研项目/wechat-input-connector/src/Connector.Windows/FocusedInputProbe.cs:264) 将 element 非空直接视为已绑定前台；287 行也将任意 element 非空视为目标。325–339 行的 UIA 控件比较抛出 ProbeRefusal 后被同层 catch 吞掉。

影响：普通非编辑 UI 元素可能通过判定；同一窗口内换了控件时，保护可能失效。这是源码可确定的逻辑缺口，尚未复现成一次实际误输入，也不能据此断言就是此前“收到回执但没有文字”的唯一根因。

最小改动：必须以真实窗口祖先关系、UIA 祖先和可编辑能力证明目标；无法证明就本条留待输入。宿主应用允许跨进程编辑器，不能粗暴要求所有 PID 相等。安全拒绝不能被宽泛 catch 消解，派发前核对同一控件及当前状态。保留无需绑定应用，不引入全局应用白名单。

验收：同一窗口换控件、非编辑按钮、密码/只读框、目标消失、UIA 比较异常均不派发；可信跨进程编辑器仍可输入。加入实际 Windows 适配验证，不能只测试已经构造好的 TargetObservation。

### 2. 正文换行与“提交”必须分离

证据：[FocusedInputProbe.cs:67](D:/project/01-自研项目/wechat-input-connector/src/Connector.Windows/FocusedInputProbe.cs:67) 和 helper 185 行将 CR/LF 转换为物理 Enter，即使 autoEnter=false 仍发生；55 行的额外 Enter 没有在正文派发后重新核对焦点，也没检查该次 SendInput 返回数量。helper 请求只有 Text / OriginProcessId，不传 autoEnter，两个后端行为不同。

影响：多行正文在部分聊天框或终端可能触发发送/执行；正文输入后焦点变化时额外 Enter 可能落到别处。关闭“输入后回车”不能阻止正文中的 Enter。

最小改动：明确区分文字换行和提交动作，统一两个后端的选项语义。支持可靠多行文本插入的控件使用文本通道；通用按键后端对不能安全保持换行语义的多行内容拒绝自动派发并保留记录，不擅自把换行改空格或改剪贴板。提交仅在显式开启且刚核对目标时执行；结果不明后绝不另试一套后端。新安装建议默认关闭额外回车，已有用户设置不擅自改动。

验收：autoEnter=false 不因正文换行而产生提交键；目标在文本与提交之间变化时不发送 Enter；两后端的回车语义一致。完整保留正文，不以删除换行换取“成功”。

### 3. 将 UIA 输入从界面线程中隔离

证据：[FocusedInputProbe.cs:31](D:/project/01-自研项目/wechat-input-connector/src/Connector.Windows/FocusedInputProbe.cs:31) 在 async 方法真正挂起前同步执行 ExecuteDirect；CaptureFocus 包括同步 UIA 访问和最多约十万字符的文档读取。当前调用链从 WPF 会话及快捷键进入，主路径没有整体超时，只有抛出异常才转 helper。界面和接收循环可能被慢 UIA 调用拖住，这是风险推断，未做卡死注入。

最小改动：复用已有按需 helper，让涉及 UIA 的完整单次输入在独立 MTA 工作线程执行，父进程负责持久化、超时、取消及关闭 Job。任何可能的派发都在一个已选定的执行路径中完成；禁止父进程先试输入、异常后再在子进程重复尝试。输入串行锁保留，超时后不累积无限挂起线程。尽量减少派发前全文读取；不恢复用户已取消的写入后结果回读。

输入超时不会自动重发本条；后续新消息继续尝试。接收循环与输入串行处理先保留现状并给每次输入设上限，暂不为吞吐量引入额外持久化队列。

验收：模拟 UIA 挂住、helper 退出、父进程退出、取消发生在派发前后；界面仍响应，子进程不残留，同条不重复输入，下一条可以继续。超时发生在哪个阶段必须可区分。

### 4. 收紧正式运行目录的写权限

本机只读权限检查：当前 .local 和 artifacts/simple-input/Connector.Probe.exe 继承了 Authenticated Users 的 Modify 权限。其他有该写权限的本机账号可以破坏状态文件或替换可执行文件；DPAPI 不保护文件的可用性，也不防止可执行文件被替换。本轮没有尝试利用或修改 ACL。

最小改动：正式版本将程序与数据放到明确的当前用户目录，分别核对目录及文件 ACL；禁止普通其他用户写程序及数据，保留必要的 SYSTEM / 管理员权限。开发仓库照常保留，不递归修改整个项目盘权限。现有 .local 迁移应为一次性、可回退操作，先备份、校验身份和状态，再切换路径；不能静默在祖先目录搜索并绑定另一份状态。

DPAPI CurrentUser 仍保留：它的边界是当前 Windows 用户，不是应用独有保险箱；同账号恶意进程及已被攻陷的系统不在本工具可解决的边界内。不要用额外硬编码密钥制造虚假的应用隔离。

## 第二批：为日常长期运行补齐的小机制

### 5. 保存故障恢复，而非只有正常替换测试

[ProtectedFile.cs:9](D:/project/01-自研项目/wechat-input-connector/src/Connector.Windows/ProtectedFile.cs:9) 已有密文临时文件、落盘和替换；现有测试验证正常替换，没有覆盖磁盘满、损坏、进程在写入/替换间退出。当前加载失败会终止收发，属于有意保守行为。

增加格式版本、结构校验、最多一份上一版有效加密快照以及有界大小校验。临时文件与目标保持同卷；测试中途失败时应至少保留一份可读取状态。恢复旧快照必须明确标记为恢复状态，不能假装拥有最新游标或自动补输可能已经执行的消息；旧快照只能辅助恢复记录，不能提供无损或恰好一次保证。不能通过另加 CRC 来冒充认证保护。

设置文件也应临时写入后替换；保存失败如实显示。当前 PillWindow.SaveSettings 的 catch 全吞可能使用户以为设置已保存，重启后却回到旧值。故障时停止相关副作用，不新增日常“暂停”功能。

### 6. 历史和队列有上限，去重记录单独保留

[ReceiptCoordinator.cs:92](D:/project/01-自研项目/wechat-input-connector/src/Connector.Core/ReceiptCoordinator.cs:92) 持续追加 Events，211 行的 Prune 只清理回执及上下文，不清理历史正文；每次状态变化又序列化并加密整个快照。长期增长将同时影响内存、写盘延迟和历史隐私。

先使用固定且有界的保留规则，不做复杂配置中心。建议初始正文上限为 7 天 / 1000 条 / 合计 10 MiB，任一到达时优先清理已结束记录；这是待确认的产品建议，不是已测试容量。去重 ID 及终态摘要与正文分离，保留覆盖已确认的协议重投窗口；未确认协议窗口前不能仅随正文删除去重键。

待输入与执行中记录不能被历史清理静默丢弃；为活动队列单独设容量，满时显式拒绝新的自动输入并给出原因，不无声覆盖旧条目。异常阶段归档、日志和旧备份也设轮换上限。只有真实数据表明有界快照仍然太慢，再迁移 SQLite；现在无需引数据库。

### 7. 保留失败原因，分清会话有效与网络健康

[ReceiptSession.cs:123](D:/project/01-自研项目/wechat-input-connector/tools/Connector.Probe/ReceiptSession.cs:123) 丢弃 NativeProbeResult.Reason，只把状态返回 Core；Queued 又统一 ReasonCode=ready。于是密码、权限、无焦点和 UIA 故障容易被折叠成同一结果。[ReceiptSession.cs:146](D:/project/01-自研项目/wechat-input-connector/tools/Connector.Probe/ReceiptSession.cs:146) 用 Connected 布尔生成 connected，即便 Phase=retrying，含义也不等于当前网络可用。

增加少量固定枚举：目标不可编辑、连接器自身前台、焦点变化、锁屏、权限不兼容、超时、存储失败等。记录阶段、耗时、输入后端、尝试计数及版本号，避免真实正文、窗口标题、凭据和原始服务端错误。保存原因与回执映射统一；本地历史显示同一事实。

保留默认绿色标识，同时用短文字表达“正在重连”“需要扫码”“当前没有输入框”；真实故障不伪装为输入成功。最近成功收件/轮询时间和失败类型足以排查，不增加监控平台。普通回执继续不包含正文。

### 8. 网络重试与回执堵塞应能自行收敛

[ReceiptSession.cs:85](D:/project/01-自研项目/wechat-input-connector/tools/Connector.Probe/ReceiptSession.cs:85) 已有有上限指数退避，保留并加入少量随机抖动；对明确永久协议错误与临时网络错误区分处理。空轮询若服务器异常快速返回应有最低间隔，休眠恢复后旧消息继续遵循新鲜度规则，不批量补打。无需心跳守护服务。

[ReceiptCoordinator.cs:175](D:/project/01-自研项目/wechat-input-connector/src/Connector.Core/ReceiptCoordinator.cs:175) 容量满会持久标记 OutboxFull，而 CompleteSend / Prune 清空后并不自动清除该原因。应在容量恢复后仅解除 OutboxFull，自身不改变用户 AutoInput，也不解除 SessionExpired、存储或旧恢复阻塞，不补打积压。保留独立查询容量和稳定 client ID。此处的容量保护不同于用户已经取消的“结果不明自动暂停”。

### 9. 生命周期、升级和维护

保留单实例和按需 helper。关闭时取消并有界等待接收/回执/输入；真正保存失败不进行盲目后台重启。检查 HttpClient、CancellationTokenSource、托盘 Icon/GDI 句柄及关闭事件的释放；原生 HICON 创建后按所有权明确销毁。未知运行状态不由循环重启掩盖。

发布加入清晰的应用版本 / commit、锁定还原、依赖漏洞检查、测试和 Release 构建；生成校验值帮助核对包与运行版本，面向他人分发时再考虑签名。哈希本身不证明发布者身份。自包含发行版本需随 .NET 安全更新重新发布，不能仅依赖操作系统补丁。版本独立目录、稳定启动入口、旧版可回退；升级不覆盖 .local，不混入凭据。当前尚无 .github 工作流，先用一条 Windows CI 流水线即可。

Program.cs 仍含不由 Main 正常入口创建的旧 ProbeForm 及另一套输入逻辑；确认无入口和测试依赖后移到开发工具或删除，减少以后误改、误发旧行为的机会。它不是当前正在运行的输入路径，不把旧窗体的暂停逻辑当作现版行为。

## 效率：先测再减，不牺牲输入前落盘

单次运行快照：当前进程响应正常，工作集约 144.7 MiB、句柄约 926；.local 当时共 18 个文件、约 128 KB。诊断显示 45 条记录、32 条待输入、12 条已派发、1 条结果不明，回执待发 0。数据只用于说明当前规模；一次快照不能证明存在/不存在内存泄漏、稳定延迟或真实文字已写入。

优先减少不必要的 UIA 全文读取、历史全量重建和诊断磁盘刷新；历史窗口使用虚拟化及增量更新，空闲时不高频扫描控件。输入前 Inserting 落盘、结果和回执同次落盘的关键写入不能为了“快”改成延后保存。接收、保存、焦点定位、派发和回执分别计时，观察 P50/P95 与进程工作集/句柄趋势，不宣称未经测量的“2ms 基线”。

建议做一次 8–24 小时真实桌面试跑，覆盖记事本、浏览器普通输入框及后续 Codex/Antigravity 适配场景；失效/锁屏/无焦点不算成功输入。接受标准是错误目标派发为 0、重复自动尝试为 0、故障后新消息可继续处理，且句柄/内存不持续无界增长；这些标准尚未验收。

## 最小实施顺序

1. 先收紧目标判定、按键语义和受控 helper 执行；给出不泄密的具体失败原因。这一批最直接关联现有“有回执但无文字”的诊断与风险控制。
2. 实施已确认的桌面交互和简单历史，同时完成目录迁移、保留上限、存储故障测试及容量恢复。新旧状态兼容与回退一起做。
3. 补齐版本、日志轮换、依赖检查和 Windows CI，然后做一次实际长时间运行。只在测量证明瓶颈后优化快照存储或接收吞吐。

本评估不是未经确认的实施授权，不新增截图上传、自动剪贴板保底、远程 shell 或任意脚本。若以后增加这些能力，需要单独定义权限与数据出站边界。

## 验证与参考

本轮执行 `./scripts/dev.ps1 test WeChatInputConnector.sln --no-restore`，Core 86 / Windows 36，共 122 项通过、0 失败。现有测试主要验证策略与状态机，不替代真实输入焦点、卡死、断电和协议端到端测试。

- [Microsoft：UI Automation 线程约束](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-threading)：UIA 应离开界面线程，使用不持有窗口的 MTA 线程；使用隔离进程是本评估基于现有 helper 提出的工程选择。
- [Microsoft：SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)：返回的是进入输入流的事件数，受到 UIPI 和当前按键状态约束；不能据此证明目标应用已保存或提交正文。
- [Microsoft：DPAPI 当前用户边界](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.dpapidataprotector.scope?view=netframework-4.8.1)：当前用户凭据下运行的其他应用也在该保护范围内；它不构成同账号进程隔离。
